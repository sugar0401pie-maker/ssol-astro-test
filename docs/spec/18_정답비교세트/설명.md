# 18. 출생차트 정답 비교 세트

## 무엇인가
가상의 테스트 출생 30건(T01~T30)의 출생차트 "정답"과, 그 정답을 엔진(`07_엔진_프로토타입.py`)과 비교한 결과입니다.

- **정답은 엔진과 독립적으로 계산했습니다**: skyfield 1.55 + JPL DE421 천체력 사용. 엔진은 astronomy-engine(VSOP87 계열)을 씁니다. 코드도 천체력도 서로 다르기 때문에, 두 결과가 맞으면 엔진을 믿을 수 있습니다.
- 좌표계: 회귀황도, 지구 중심 겉보기 위치, 그날의 참 황도·참 춘분점(엔진과 같은 정의)
- 하우스: 홀사인(ASC 별자리 = 1하우스)
- ASC·MC: GAST(겉보기 항성시) + 경도 = LST, 참 황도경사 사용. 계산한 ASC가 MC의 동쪽 180° 안에 있는지, 동쪽 지평선(고도 0, 떠오르는 쪽)에 있는지 자동으로 검산합니다.
- 시간대: IANA zoneinfo(Asia/Seoul 등)를 정답으로 봅니다.

## 파일
| 파일 | 내용 |
|---|---|
| `정답세트.json` | 출생정보, 정답값, 메타데이터(천체력·버전·좌표계·생성일), 엔진 비교 결과 |
| `정답세트.xlsx` | JSON과 같은 데이터. 시트: 읽어주세요 / 출생정보 / 정답(출생×천체 360행) / 엔진비교 / 시간대비교 / 요약 |
| `make_reference.py` | 전체를 다시 만듭니다(정답 계산 → 엔진 비교 → JSON·엑셀 저장) |
| `compare_engine.py` | 엔진 비교만 다시 돌립니다. FAIL이 하나라도 있으면 종료코드 1. `--strict-tz` 옵션을 주면 시간대 규칙 불일치도 FAIL로 셉니다 |

실행(이 폴더에서): `python make_reference.py` 또는 `python compare_engine.py`
필요한 패키지: skyfield, skyfield-data, openpyxl, astronomy-engine

## 테스트 출생 구성 (30건)
- 일반 한국 출생 11건 (1965–2010, 서울·부산·제주·경기·광주, 시간대 다양). T06은 `08_샘플_엔진출력`과 같은 출생정보
- 한국 서머타임: T11(1987), T12(1988), 경계 시각 T13(1987-05-10 01:30), T14(1988-10-09 01:30)
- 한국 과거 시간대: T15(1958), T29(1960). 표준시 UTC+8:30에 서머타임이 더해져 UTC+9:30
- 자정 경계: T16(00:05 → UTC로는 전날), T17(23:55)
- 별자리 경계: T18 달(양자리 29.84°, 경계 0.16° 전), T20 태양(춘분 30분 전, 물고기자리 29.98°). 덤으로 T22 태양은 게자리 경계에서 66″ 떨어져 있습니다
- 역행: T19 수성 역행 한가운데. 이 밖에 정류 직전·직후 행성도 들어 있습니다(T17 명왕성, T02 목성, T15 해왕성: 속도가 하루 0.001° 미만)
- 해외: 뉴욕(EDT), 런던(BST), 시드니(AEDT), 로스앤젤레스(모호한 시각), 베이징(중국 서머타임), 도쿄, 호찌민, 모스크바(고위도·서머타임)

## 개발자가 자동 테스트로 쓰는 방법
1. 서버 엔진에도 같은 검사를 만듭니다. `정답세트.json`의 `births[].utc`, `lat`, `lng`를 그대로 넣고, 10행성·ASC·MC 경도를 계산한 뒤 `reference.bodies`와 비교하면 됩니다. 로직은 `compare_engine.py`를 그대로 옮기면 됩니다.
2. 경도 차이는 ±180°로 감싼 다음 초(″) 단위로 비교합니다.
3. 별자리·홀사인 하우스·역행 여부도 비교합니다.
4. 시간대 변환은 따로 시험합니다. `births[].local` + `tz`(+`fold`)를 UTC로 바꿨을 때 `births[].utc`와 같아야 하고, `tz_probes`의 오프셋과도 같아야 합니다.
5. CI에 넣어 두고 엔진이나 라이브러리를 바꿀 때마다 돌립니다.

**사람이 직접 확인할 것 (Astro-Seek 5건)**: Astro-Seek 출생차트 화면에서 하우스 방식을 *Whole Sign*으로 고르고, 현지 시각과 도시를 넣습니다. 그다음 화면에 나온 UT가 우리 UTC와 같은지, 행성·ASC·MC 도수가 1′ 안에서 맞는지 봅니다.
추천: **T06**(샘플), **T15**(1958 서울, UTC+9:30), **T18**(달 경계), **T21**(뉴욕 서머타임), **T28**(모스크바 고위도)

### 한국 시간대 규칙 불일치
비교 대상은 프로토타입 규칙(`13_프로토타입/index.html`의 `koreaOffset`)입니다. 이 규칙은 날짜 단위로 판단하고, 1954-03-21~1961-08-09의 +8:30과 1987·88 서머타임만 처리합니다. zoneinfo와 비교한 결과는 다음과 같습니다.

| 경우 | zoneinfo | 프로토타입 | 차이 |
|---|---|---|---|
| T13 1987-05-10 01:30 (서머타임 시작 02:00 전) | +9 | +10 | 1시간 |
| T14 1988-10-09 01:30 (서머타임 종료 03:00 전) | +10 | +9 | 1시간 |
| T15 1958-07-15 12:00 | +9:30 | +8:30 | 1시간 |
| T29 1960-05-20 08:00 | +9:30 | +8:30 | 1시간 |
| 추가 점검: 1949·1951 여름 | +10 | +9 | 1시간 |
| 추가 점검: 1956·1957·1959 여름 | +9:30 | +8:30 | 1시간 |
| 추가 점검: 1987-10-11 01:30, 1988-05-08 01:30 (전환일의 전환 시각 전) | 각각 +10, +9 | +9, +10 | 1시간 |

출생 4건과 추가 점검 9건이 다릅니다(엑셀 '시간대비교' 시트). 원인은 두 가지입니다.
1. 1948–1960년 서머타임이 규칙에 빠져 있습니다.
2. 1987·88년 전환일 당일에는 시각(02:00 / 03:00)을 보지 않고 날짜만 봅니다.

→ 마스터스펙(01) 37행대로 서버는 IANA zoneinfo로 바꿔야 합니다. 1시간 차이가 나면 ASC가 약 15° 움직이므로 상승궁·하우스가 바뀔 수 있습니다.

## 만들면서 알게 된 점
- **1972년 이전 UTC 처리**: skyfield는 1972년 이전 UTC를 "TAI−10초"로 가정합니다. 그래서 1958년 출생이면 UT1과 약 10초, 1965년이면 약 7초 어긋나고, 그 결과 ASC·MC가 최대 약 170″ 틀어집니다. 실제 당시 상용시는 UT1과 0.1초 안으로 맞춰져 있었으므로, 정답 계산에서는 1972년 이전을 UT1로 해석했습니다. 엔진(astronomy-engine)은 입력 시각을 UT로 보기 때문에 원래 맞게 계산하고 있었습니다. 서버를 다른 라이브러리로 옮길 때 같은 함정이 있는지 확인하세요.
- **로스앤젤레스 1990-11-04 01:30은 모호한 시각이 아닙니다.** 1990년 미국 서머타임 종료일은 10-28이었습니다. 그래서 T24는 1990-10-28 01:30으로 바꾸고 fold=0(첫 번째 01:30, PDT UTC−7)을 썼습니다. 서비스에서 이런 시각이 들어오면 사용자에게 어느 쪽인지 물어보거나 fold=0으로 정해 두세요.
- **역행 판정 방식이 다릅니다.** 엔진은 ±1일 경도 차이로, 정답은 ±1시간 중앙차분으로 판정합니다. 정류 직전·직후 행성(속도가 하루 0.001° 미만)이 3건 있었는데 이번에는 모두 일치했습니다. 다만 그런 경계에서는 방식에 따라 결과가 갈릴 수 있습니다.
- **황도경사 계산**: 엔진은 ASC 계산에 평균 황도경사의 1차식을 씁니다(장동 미반영, 최대 약 9″). 결과 차이가 ASC 19″ 안이라 문제는 없습니다.
